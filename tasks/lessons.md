# Lessons & Patterns Registry

## Operational Principles
1. **Candidate Truth Invariant**: Never allow any module to invent, extrapolate, or falsify experience, job titles, or skills.
2. **Salary Eligibility Precision**: Disclosed minimum salary must be $\ge$ 30 LPA or span $\ge$ 30 LPA ceiling. Any range whose maximum ceiling is $< 30$ LPA must be rejected immediately.
3. **Zero-Exaggeration & Proof-Based Audit Rule**:
  - Never claim a fix is implemented without rigorous codebase verification.
  - Pre-flight application leases MUST be committed immediately to SQLite and enforced in `has_applied_to_job()`.
  - Candidate answer resolvers must NEVER use hardcoded fallback numbers (e.g. "2", "5", "35.0")—every response must derive strictly from `CandidateTruth` or return `can_answer=False`.
  - Phase gate validation must be proof-based and check real physical evidence files on disk, not just count raw attempted records in SQLite.
  - Centralize verification rules in `ApplicationVerifier` so text heuristics never claim `APPLIED_CONFIRMED` without authentic badge or reference proof.
4. **Safe Automation**: Never attempt to bypass CAPTCHA, MFA, or rate limits. Halting and logging `BLOCKED` preserves account integrity.
5. **Idempotency**: Every job processing step must be idempotent and recoverable from SQLite state. Pre-flight intent leases and unique constraints must protect against duplicate external actions across crashes.

## Log of Lessons Learned
- **Target Role Focus**: Prioritize Oracle Cloud Administrator / Architect and LLMOps / AI Architect roles specifically across search and qualification.
- **Salary Floor Adjustment**: Minimum compensation floor updated from ₹20 LPA / ₹25 LPA to ₹30 LPA (configurable via .env; no upper ceiling; undisclosed allowed).
- **Application Transparency**: Explicitly distinguish between verification/offline test runs and live employer submissions in reports so the user has zero ambiguity about applied roles.
- **Recruiter Engagement Timing (2x Daily Schedule)**: Running twice daily at 09:00 IST (03:30 UTC - morning Resdex login & overnight job postings) and 14:00 IST (08:30 UTC - post-lunch candidate screening) ensures maximum visibility and top-of-inbox placement for recruiter screening batches.
- **Current Employer Safety Invariant**: Candidates must NEVER apply to or be visible to their current employer (Cognizant/CTS). Enforce hard blocklists in config, discovery, qualification, and application engines, and ensure current employer records are immediately blocked from all pipeline activity.
- **Production Database & Reporting Cleanliness (Zero Mock Pollution)**: Never allow offline test fixtures, unit test records, or mock application IDs to be written to or remain in the production SQLite database (`naukri_career_agent.sqlite`). Production database and reports must ONLY contain real live applications submitted through authenticated browser automation that exist in the user's Naukri account history (`https://www.naukri.com/myapply/historypage`). Test suites must ALWAYS use an in-memory database (`sqlite:///:memory:`) or isolated test database, ensuring zero mock pollution.
- **Precise DOM Matching & Live Account History Verification**: Never use loose substring matches (e.g. `span:has-text('Applied')`) because Naukri pages contain substrings like "Early Applicant", "Applicants: 50+", or "Applications viewed". Instead, strictly verify specific CSS classes (`.already-applied`, `span.already-applied`) and exact text matches. The ultimate ground truth is the live account history page (`https://www.naukri.com/myapply/historypage`); an application is only deemed successfully submitted if it increments the user's live Naukri application counter and displays on the history timeline.
- **Pan India Filter & Location Boundary Freedom**: Restricting job discovery to a single city or rigid set of metro locations artificially throttles opportunity discovery in senior architecture domains (OCI Architect, GenAI/Agentic AI Lead). Removing location restrictions and adopting Pan India / Remote / Hybrid defaults expands the discovery pool to high-yield national opportunities (e.g. TCS Pan India openings, multi-hub enterprises, remote architectures). Candidates open to national mobility should have screening questions automatically answered as Pan India / Relocation: Yes.
- **Executive Resume Depth & Non-Truncating PDF Generation**: Senior profiles (10–15+ years) cannot use simplified single-paragraph summaries or flattened bullet lists. They require an executive summary articulating enterprise scale and leadership, domain-categorized competencies, and bold lead-in bullet points with concrete metrics (~60% deployment reduction, ~40% incident reduction, ~50% DBA reduction). PDF generation must NEVER use character-slicing or bullet-capping; headless Chromium print rendering guarantees 100% text fidelity, exact pagination, and 100% ATS score.
- **Database & Storage Retention Invariant**: Continuous autonomous execution generates ephemeral data (unqualified jobs, debug inspect screenshots, log files, unapplied draft resumes). Retention rules must safely prune stale records and execute SQLite VACUUM to reclaim disk space while enforcing permanent immutability on confirmed applications (`APPLIED_CONFIRMED`), legal visual evidence (`*_already_applied.png`), and master resumes (`resumes/master/`).
- **Zero Dummy Job Invariant & Non-Overwriting Qualification State**: Never allow mock or synthetic jobs (e.g. `job_oci_genai_101`, `nk_...`) to linger in the database or be emailed to the user, as synthetic URLs inevitably return 404 ('Page Not Found') upon clicking. Production scraping fallbacks must return empty lists rather than generating synthetic jobs. Furthermore, qualification evaluation (`QualificationAgent.evaluate_job`) must NEVER overwrite or demote the status of jobs that are already in `APPLIED` or `APPLIED_CONFIRMED` status. All reports, interview dossiers, and emails must strictly enforce regex verification for real numeric Naukri IDs (`^\d+$`) and reachable URLs.
- **Complete Eradication of Dummy Fallback & Synthetic Applies**: Production codebase must contain zero fallback logic that creates mock jobs or simulated apply confirmations (`MOCK_CONF_...`, simulated `CONF_...`, `SIMULATED_DRY_RUN`). At no point should any component simulate an application and mark it as `APPLIED` in the database. In dry-run or offline mode, application processing must halt cleanly at `JobStatus.APPLICATION_READY`, with `confirmation_detected=False` and `confirmation_reference=None`. The only applications that can ever be recorded as `APPLIED` or `APPLIED_CONFIRMED` are authentic live browser submissions verified against the official green `.already-applied` badge on Naukri. Unit and integration tests must use test-level fixtures (MagicMock / test data) rather than embedding mock generators into production adapters.
- **Dual-Track Multi-Pillar Qualification (No Monolithic Cross-Track Penalties)**: When a candidate has multi-pillar expertise across distinct career domains (e.g., Core OCI/Cloud Architecture vs. Emerging GenAI/LLMOps Architecture), qualification matching must evaluate each listing against the candidate's best-aligned track (`overall_score = max(track_cloud, track_ai, track_hybrid)`). Monolithic formulas that require both tracks simultaneously (e.g., penalizing an Oracle Cloud Infrastructure role for lacking GenAI keywords, or an AI Architect role for lacking Oracle Exadata) cause false rejections of high-value opportunities.
- **Enriched Search Card Data Scraping in Browser Automation**: Search result scrapers must never rely solely on job titles. They must extract all available card context (skill tags, JD snippet, and query context) to ensure downstream qualification engines have sufficient semantic signals to accurately compute domain alignment.
- **Strict Confirmation Invariant Alignment (Post-Submit Reload + Badge Assertion)**: Transient URL substrings (`saveapply`) or generic page text ("applied to") are not definitive proof of submission. Verification must strictly reload the canonical job listing and assert the visible `.already-applied` badge before marking `APPLIED_CONFIRMED`. Any ambiguous intermediate state must be marked `SUBMISSION_UNVERIFIED`.
- **Pre-Flight Atomic Intent Leases & Idempotency Across Crashes**: The irreversible portal submission click must never occur without prior persistence of an atomic intent lease in the database with a `UNIQUE(job_id)` constraint. This guarantees that process crashes, network timeouts, or unhandled exceptions after clicking submit cannot result in duplicate application attempts.
- **Fail-Closed Security, Authentication & Barrier Gates**: Authentication status (`_ensure_authenticated()`), CAPTCHA, MFA, OTP, and payment gates must fail closed. If authentication is invalid or any barrier is detected, the agent must immediately abort and record `APPLICATION_BLOCKED` or `NEEDS_MANUAL_INTERVENTION` instead of continuing blindly.
- **Truth-Driven Form Answering & Verified PDF Upload**: Never auto-select "YES" or any chip without resolving the specific prompt label against `candidate_facts.yaml`. Unrecognized controls (radios, selects, custom text inputs) must trigger a graceful halt to `NEEDS_DATA`. Furthermore, verify that the intended tailored PDF (not DOCX) was successfully uploaded and accepted before submitting.
- **Short-Lived Transactions & Connection Durability**: Never run an entire multi-step orchestrator pipeline inside a single long-lived database transaction. Commit state transitions immediately before and after side effects. Configure SQLite with WAL mode, busy timeouts, and foreign key enforcement on every connection to eliminate lock contention between orchestrator runs and retention routines.
- **No Production Database Seeding with Historical Fixtures**: Production database initialization (`init_db()`) must never load pre-populated historical applications from `seed.sql`. Seeds belong strictly in test fixtures. Phase validation must audit current run execution telemetry and proof timestamps rather than static seed rows.
- **Deterministic Resume Naming & Format Parity**: Resume artifacts must include the immutable `job_id` in their filename (`Saket_Saurav_<Company>_<JobID>.pdf`) to eliminate collisions between same-day postings with identical job titles. The browser uploader must upload the validated PDF version.
- **Unified Salary Configuration**: Salary thresholds must be defined in one authoritative location (`config.yaml` at ₹30 LPA) and referenced dynamically across adapters, parsers, tests, and documentation, removing all divergent legacy constants.
- **Current Compensation Parity (₹30 LPA Floor)**: Candidate's baseline current compensation is ₹30 LPA. The career agent must strictly reject any disclosed opportunity offering less than ₹30 LPA to ensure no downward compensation drift. Postings with undisclosed compensation remain eligible to capture senior unposted salary bands.
- **Comprehensive Daily Report Backfill (Confirmed Applications + External Opportunities)**: When aggregating or backfilling daily report data from persistence (`JobRepository`), reporting and orchestrator logic must never retrieve only `APPLIED_CONFIRMED` records. It must simultaneously query `EXTERNAL_APPLICATION_REQUIRED` and `NEEDS_MANUAL_INTERVENTION` so that curated enterprise external portal opportunities (e.g. Workday, Greenhouse, Taleo) are consistently presented with 1-click apply action buttons in the daily report and email dispatch.
- **External Opportunities Quota Exemption**: External portal opportunities are manual candidate actions on enterprise career sites that do not submit through automated Naukri direct channels. Consequently, they must never be throttled or stalled by on-platform automated daily application quotas.
- **Salary Range Ceiling Rule (Max Range $\ge$ ₹30 LPA Acceptable)**: When a job posting discloses a salary range (e.g., 20–35 LPA, 25–40 LPA, 25–32.5 LPA) where the lower bound starts below ₹30 LPA but the upper bound reaches or exceeds ₹30 LPA, the opportunity is acceptable and marked `ELIGIBLE` to preserve candidate upside and negotiation potential. A posting is strictly marked `REJECTED` only if its maximum disclosed salary ceiling is below ₹30 LPA (e.g., 15–25 LPA, 18–28 LPA) or if a single disclosed rate is below ₹30 LPA.
- **GitHub Actions Multi-Schedule Cron Syntax Invariant**: Never use comma-separated hour or minute values in a single cron expression (e.g. `cron: '30 3,8 * * *'`). GitHub Actions' scheduler parser requires separate independent `- cron:` entries for each trigger window (e.g. `- cron: '30 3 * * *'` and `- cron: '30 8 * * *'`). Using comma-separated lists in cron hours causes GitHub's backend scheduler to silently fail to register or drop scheduled workflow runs.
